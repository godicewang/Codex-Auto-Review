# AutoReview

**安静审计，意见随下一轮需求传达。**

[中文首页](README.md) · [English](README.en.md) · [提示词与输入说明](docs/prompts.md) · [架构](docs/architecture.md) · [验证记录](docs/validation.md)

AutoReview 在 Codex 完成有代码变更的一轮后，在确认有 Codex 写入工具产生的改动后，启动独立、只读的后台 Codex 会话。它只输出有证据的 Bug 和明确修改建议。每份完成报告进入消息队列；你继续提出需求时，hook 批量传给主 Codex，由主对话复核、决定如何修复。

**后台不改文件、不回写补丁、不运行安装或测试、不提交或推送。**

## 安装与入口

需要 Node.js 20.11+、Git、支持 plugins/hooks/App Server 的已登录 Codex CLI。下载或克隆项目后，在项目目录执行：

```sh
npm run setup -- --project /你的/Git项目路径
```

无需 `npm install`、编译 JavaScript、数据库或额外 API key。macOS 安装器会使用系统 Swift 工具构建 `~/Applications/AutoReview.app`，并打开原生悬浮窗。缺少 Xcode/Command Line Tools 时会打开相同的本地网页。

**入口在哪里：**

- **Codex 项目对话顶部 → Actions / 运行操作菜单 → AutoReview**：点击即连接并开启此任务对应的项目，无需输入路径。安装器会配置官方动作。当前对话没有刷新时切换项目或开启新对话；在本地环境设置中选中项目的环境。
- **随 Codex 显示的 AutoReview 面板**。切到浏览器等其他应用、隐藏或最小化 Codex 时，面板和小入口都会隐藏；回到 Codex 后恢复此前状态。点击 `−` 或窗口关闭按钮，收起为 **◉ AutoReview** 小入口；点击它重新展开，可以拖动边缘移动。
- 屏幕顶部菜单栏的 **◉ AutoReview**，可以重新显示窗口或重新连接服务。
- Finder → 个人目录 → Applications → **AutoReview.app**；或者随时在源码目录执行 `npm start`。
- 对安装了插件的新 Codex 对话说「打开 AutoReview 悬浮窗」。

打开动作使用 [Codex 官方本地环境 Actions](https://learn.chatgpt.com/docs/environments/local-environment)，面板是独立原生悬浮窗。你也可以要求 Codex「在右侧浏览器面板打开 AutoReview」。若项目已有复杂自定义环境，安装器会保留原配置；在面板点击“添加打开按钮”取得命令，在 Codex 的“添加动作”中粘贴即可。

## 第一次怎么用

1. 安装器自动配置并验证本插件的六个生命周期事件，无需进入 Codex CLI。
2. 安装或升级后，**开启新的 Codex 对话**。若要继续原来的任务，在面板点击 **接入帮助 → 打开 Codex 插件页**，将 AutoReview 关闭再开启一次。
3. 点击当前任务顶部 **Actions → AutoReview**，自动连接并开启当前项目。项目来自这次动作的工作目录，不需要填写路径。
4. 面板下拉框可以查看已连接的不同项目，各项目的开关独立；已开启项目都能继续审计，切换面板视图不会暂停其他项目。
5. 正常开发。Codex 写入工具确实造成改动后，回合结束时自动冻结并审计；报告完成后排队，随下次消息传达。

连接当前项目的按钮放在 Codex 顶部，保证使用该任务的真实工作目录。独立悬浮窗没有公开接口读取“当前显示的是哪个任务”，因此不猜测最近活动会话，也不要求填写路径。如果新项目尚未配置动作，可在 Codex 的“添加动作”中使用安装器提供的稳定命令，或对该任务说“开启 AutoReview”；插件使用任务已有的项目目录完成连接。

安装器通过官方 `hooks/list` 读取本插件的精确定义，校验来源与命令，再通过 `config/batchWrite` 写入本插件的信任摘要并读回验证。不会关闭全局检查，也不批准其他插件。面板的“接入帮助”始终可用；“核对配置”可修复安装登记，但不会刷新已有 GUI 任务。

面板会区分“已开启，等待 Codex 会话接入”和已经收到事件的状态。安装器在独立进程里刷新配置，无法刷新正在运行的桌面宿主；Codex 插件页的开关则由桌面宿主执行刷新。只打开页面不会刷新。最近事件属于此项目，可能来自其他任务，不代表当前可见任务已接入。排查依据和恢复步骤见[接入故障排查](docs/hook-troubleshooting.md)。

首次使用显示“等待首次审计”。上次审计失败会显示原因和“查看失败记录”，不会用空队列冒充无问题结论；此前已完成的待传达报告仍保留。

## 意见如何传给主 Codex

官方 `UserPromptSubmit` 的 `hookSpecificOutput.additionalContext` 会给本轮增加模型可见的上下文；不改写你的输入框，也不保证它在界面上出现在用户消息之前。上下文要求主 Codex：**先核对上轮问题是否仍成立，再按当前需求考虑修复；本轮用户要求优先。**

- 每份成功完成的报告都进入持久化 FIFO 队列，包括简短的“未发现明确 Bug”结论；新报告不覆盖旧报告。
- 每次用户消息领取同项目、同会话的待传达报告；同一回合中的补充消息也可领取新完成的报告。不同项目和其他会话互不领取。
- **一次最多 48,000 字符**（UTF-16 计数，常见中文字符计 1）。通常一次传完；超过上限时按完整报告分批，剩余内容留给下一条消息，不截断问题和建议。
- 下一次输入时审计尚未完成：立即处理新需求，不等待；结果完成后继续入队。
- 主代码已经变化：报告仍传达，并标明“基于旧快照”，要求主 Codex 重新核对行号、触发条件和结论，跳过已修复或不适用的问题。
- 失败、取消和未完成的任务不入报告队列。无问题报告也不意味着测试通过。
- 手动“审计当前快照”完成后，由同项目的下一条主对话消息领取，不跨项目。
- 传达后从待传达队列移除，历史仍可查看；重启后未传达队列保留。清理历史不会删除待传达报告。

完整 hook 内容发送成功并确认后才出队；传达失败会保留到下次。确认请求失败或并发输入时，同一报告可能再次出现，主 Codex 会按 reviewId 跳过已处理项。“已发送”不代表模型已处理或 Bug 已修复；Codex 在收到内容后崩溃等情况没有端到端消费回执。

只有主 Codex 可以根据你的需求修改源码。只读审计者本身无法与主对话争抢文件。

**审计的是上一轮结束时冻结的代码。** 排队等待或审计过程中，你继续编辑、添加或删除文件，都不会改变正在审计的副本。审计成功、失败、超时或取消后，会等待审计进程退出，再自动删除副本和其中的临时 `.git`，回收不再使用的内容。不会在你的仓库中留下分支、worktree 或 Git 对象。异常退出的残留在下次服务启动时清理。

**整轮工作和回答结束后才启动自动审计。** 写入工具全部结束且收到 Stop 时先建立候选快照，再通过官方 App Server 的回合状态确认对应任务/回合为 completed。若 Codex 继续工作，就撤销候选并等待最终结束；确认失败最多等待 120 秒，然后跳过并清理。单个工具结束或文件短暂无变化都不会触发审计；查询只读取生命周期元数据，不把主对话内容传给审计者。暂停、取消和退出也会中止完成状态查询并回收进程；关闭中的连接操作不会重新开启项目。

## 中文与提示词

单份报告完整 JSON 硬上限 **6,000 字符**，中文自然语言力争不超过 1,600 字；标题、证据、影响、建议也各有长度约束。提示词、输出 schema 和运行时校验共同控制篇幅。

最新需求含中文时，问题标题、证据、影响、建议和局限必须用中文。代码与路径保留原样。英文需求输出英文结论。提示词、输入字段和旧版本问题的详细说明见 [提示词审计](docs/prompts.md)。

审计仅接受高置信度、定位有效、证据完整的问题；不凑数，不报告风格偏好或推测性改进。模型仍可能判断错误，所以注入意见要求主 Codex 独立复核。

## 常用命令

```sh
npm start
node plugins/autoreview/bin/autoreview.mjs dashboard
node plugins/autoreview/bin/autoreview.mjs enable /项目路径
node plugins/autoreview/bin/autoreview.mjs disable /项目路径
node plugins/autoreview/bin/autoreview.mjs doctor
node plugins/autoreview/bin/autoreview.mjs status
node plugins/autoreview/bin/autoreview.mjs stop
npm run setup -- --uninstall
```

关闭面板会留下随 Codex 显示的小入口；退出配套应用后可通过 Codex 顶部 AutoReview 动作重新打开。关闭或退出界面不停止后台；暂停项目或 `stop` 才停止相应审计。卸载插件会停止后台并保留本地历史。原生配套应用可以在 Finder 中移至废纸篓。

面板设置可选模型和最长审计时间。默认 300 秒、一次运行一个审计；超时不自动重试。数据默认在 `~/.autoreview`，可用 `AUTOREVIEW_HOME` 指定。`AUTOREVIEW_CODEX_BIN` 指定 CLI 可执行文件路径。不要把本地带访问令牌的面板链接发给别人。

快照排除依赖目录、忽略文件及常见凭据路径，不读取 Codex 认证文件。路径规则不是敏感内容扫描器。v0.1 数据会先备份至 `state-v1-backup.json`，旧运行只保留历史，不再执行旧修复或文件恢复事务。

审计结束后保留报告和用于检查意见是否过期的内容摘要，不保留该次审计的完整源码副本。仍被其他排队/运行中的审计或当前开发回合引用的内容，等它们结束后再回收。已传达/失败/取消等普通历史最多保留 100 条。待传达队列加未完成任务最多 200 条，满时暂不接收新审计，已有报告不会被丢弃；非活动回合需求历史最多 200 条且每会话最多 12 轮；旧版恢复记录和备份保留。诊断日志超过 1 MiB 时按维护策略保留最近约 512 KiB，报告队列不受影响。无需手动 `prune` 才能清理副本；若清理失败，面板会显示原因并自动重试。

## 只审计 Codex 的改动

自动审计由官方工具事件触发，不使用目录 watcher。`PreToolUse` 和 `PostToolUse` 按工具调用 ID 配对，记录可识别写入的前后字节；`apply_patch` 只归因补丁声明的文件，shell 仅接受可识别的写入命令。只读调用、没有工具来源的人工编辑不会触发审计。工具完成后被人工覆盖的文件、版本链断裂的文件会跳过。

这不是操作系统级的作者追踪：若其他程序恰好在同一工具执行窗口内写入同一文件，无法严格区分作者；无法识别的脚本写入可能跳过。副本保留相关源码供核对调用关系，但报告范围只包括归因到 Codex 的变化。

## 一个实际例子

你完成 A 需求，后台开始审计 A 的冻结快照；你继续做 B，A 的审计不受影响。A、B 的两份报告都完成后进入队列。你再发送 C 需求，两份报告会一起交给主 Codex，它先复核哪些问题仍成立，再按 C 的要求处理。后台始终不改代码，审计用的副本已在各次完成后清理。

## 开发

```sh
npm test
npm run check
node scripts/smoke-real.mjs
node scripts/probe-installed.mjs
npm run pack:release
```

真实冒烟测试使用已有 Codex 账号，会消耗正常额度。macOS 原生外壳已本机验证；Windows/Linux 使用网页入口，仍需平台集成测试。发布包无需 npm 依赖。MIT 许可证；这是社区项目，与 OpenAI 官方的权限升级 Auto-review 功能不同。

设置和手动审计弹窗会明确显示目标项目。即使另一个 Codex 动作切换了当前查看项目，提交仍作用于打开弹窗时的项目。常见的多行 setup 配置可自动保留并添加 AutoReview 动作；只有冲突或无法安全识别的配置才需要使用 Codex 的环境编辑器。

本地实验记录保留在 `docs/experiments/`，默认不进入 Git 或发布包；不会让下载后的项目自动执行个人实验。
